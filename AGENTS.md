# AGENTS.md: правила роботи агента в проєкті korolyk\*ph

Лендінг фешн-фотографки Анастасії Королик (korolyk\*ph, Івано-Франківськ / Львів). React + Vite + TypeScript, Tailwind v4, shadcn/ui, framer-motion. Деплой: Vercel. Мова сайту й спілкування: українська. Власник працює на Windows (команди для нього давай для cmd).
Сайт затверджений візуально й працює. Головна задача при будь-якій зміні: **виконати саме те, що просили, і нічого не зламати поруч**.

## 0. Пріоритет правил (при конфлікті виграє вищий)

1. Явна вказівка власника в поточному повідомленні. Якщо вона суперечить п. 2–3, не виконуй мовчки: поясни, що зміниться, і запропонуй варіанти (розділ 1.4).
2. Захищені зони (розділ 3).
3. `STYLE-LOCK.md` і розділ 4 цього файлу.
4. Рекомендації скілів. Скіл підказує, але не змінює дизайн проєкту. Єдиний виняток: пороги доступності зі скіла `better-interface` (контраст, фокус, 320 px / 200 % zoom, `prefers-reduced-motion`, імена кнопок) не скасовуються стилем. Якщо їх виправлення змінить вигляд, спитай власника.

## 1. Як зрозуміти запит (виконуй перед будь-якою роботою)

Власник часто формулює коротко й образно. Це нормально, і догадуватися наосліп не потрібно.

### 1.1 Спершу дивись сам

Перш ніж питати, перечитай `STYLE-LOCK.md`, потрібні файли, `git log` і цей файл. Питай лише про те, чого там немає.

### 1.2 Перекажи запит (1–3 рядки, на початку відповіді)

- Що саме змінюю: секція, компонент, файл, ширини (мобільний / десктоп / усі).
- Що навмисно НЕ чіпаю (сусідні блоки, десктоп, захищені зони).
- Розмір задачі: S / M / L (розділ 7) і які перевірки з цього випливають.

### 1.3 Коли питати, а коли діяти

Правила питань:

- Спершу `AskUserQuestion`; якщо інструмента немає, пронумерований список у відповіді. Не більше 4 питань за один раз, одним блоком.
- До кожного варіанта пиши ВПЛИВ: що зміниться, що ще може зачепити, наскільки ризиково. Рекомендований варіант став першим у списку і напиши «(рекомендовано)».
- Формат: **Питання** → варіанти A/B/C з впливом → «Якщо не відповіси, зроблю A».
- Якщо власник не на звʼязку або сесія автономна, не зупиняйся: візьми рекомендований варіант, напиши на початку підсумку «Припущення: …» і не чіпай того, що не відкочується.
- Не питай про дрібниці, не перепитуй уже вирішене в цій сесії.

### 1.4 Коли запит суперечить правилам проєкту

Не відмовляй і не роби мовчки. Напиши: «Це змінить [X]. STYLE-LOCK / захищена зона каже [Y]. Варіанти: A (у межах стилю, рекомендовано) / B (як просиш, з наслідками …)».

## 2. Перед початком роботи

1. Прочитай `STYLE-LOCK.md`.
2. `git status`. Дерево має бути чистим. Мої незакомічені зміни не чіпай, не додавай до комітів, не стешуй. На момент написання це `src/components/Faq.tsx`: без прямої вказівки не торкатися.
3. Окрема гілка від актуальної (`feat/…`, `fix/…`). Один коміт на одну логічну зміну. Стиль повідомлень як у `git log`. Не пуш, не мерж, не видаляй гілки без моєї команди. Без force-push. `git rebase -i` не використовуй (редактор недоступний).
4. Визнач розмір задачі S / M / L (розділ 7).
5. Скіли: див. розділ 6. Не вигадуй відсутній скіл: скажи, що його немає, і виконай перевірку вручну.

## 4. Гнучкий стиль: як міняти вигляд, не ламаючи красу і сусідів

### 4.1 На якому рівні правити

- Власник каже «тут», «цей блок»: правка локальна (клас або компонент цього блоку). Глобальні селектори, токени й спільні компоненти не чіпай заради одного блоку.
- Власник каже «всюди», «на всьому сайті»: правка на рівні токена чи спільного класу. Спершу `grep` усіх використань, потім перевір кожне.
- Якщо локальній потребі треба змінити спільне, зроби локальне перевизначення в блоці. Спільне змінюй лише за погодженням.

### 4.2 Значення

- Лише наявні токени та кроки шкали. «Більше / менше» = сусідній крок шкали. Новий токен лише за моєї згоди, потім запропонуй додати рядок у `STYLE-LOCK.md` (сам не пиши).
- Розмір тексту та відступи, що мають змінюватись по ширині: `clamp()` на основі кроків шкали, а не набір розрізнених медіазапитів.
- Розкладка тримається на потоці (`grid`/`flex`/`gap`), а не на `absolute`, магічних числах чи негативних margin.
- `min-height` і `max-width` замість фіксованих `height`/`width`. Висота екрана: `svh`/`dvh`.
- Фото: природні пропорції, `width`/`height` в атрибутах, без обрізання `object-fit: cover` під фіксований `aspect-ratio`. Обличчя не обрізати.

### 4.3 Витримує зміну змісту

Верстка має витримати: довший чи коротший текст (нові формулювання), відсутнє фото, ширини 320–2560. Якщо текст не вміщується, спершу переверстка / перенос / `better-typography`, і лише потім зменшення. Відступи не стискати заради вміщення.

### 4.4 Інваріанти краси (звіряй із сусідніми блоками до завершення)

1. Ієрархія: контраст розмірів і ваги між рівнями заголовків не зменшується.
2. Ритм: однотипні елементи мають однакові відступи, відступи між секціями за шкалою.
3. Вирівнювання по спільних лініях (поля, сітка); оптичне вирівнювання великих літер і стрілок.
4. Чорно-біла палітра без нових кольорів, контраст тексту ≥ 4.5:1 (сірі вторинні тексти міряй, а не оцінюй на око).
5. Однакові радіуси й ритм карток, зерно по всьому сайту.
6. Повітря: новий елемент не «притискає» сусідів.

### 4.5 Без побічних ефектів

Перед правкою (M і L) запиши опорні метрики сусідів: положення й висоти елементів, `scrollHeight`, `--stack-h`. Після правки порівняй: змінитись має лише задумане. Якщо немає інструмента, перевір читанням коду, і в звіті так і напиши.

### 4.6 Анімації

Лише `transform` і `opacity`. Hover під `@media (hover: hover)`. `prefers-reduced-motion` вимикає рух (opacity можна залишити). Hero-розмиття це готовий шар `hero-blur.jpg` з crossfade через opacity. Паралакс і drift через CSS scroll-driven animations зі статичним fallback. Стан не лише рухом: має бути й статична ознака.

### 4.7 Тексти

Вставляються дослівно. Дозволена лише типографіка: нерозривні пробіли (після односкладових прийменників і сполучників), тире, кома в десятковому, лапки. Стилістику, довге тире та пунктуацію власника не «виправляй» (див. конфлікт `tastemaker` у розділі 6).

## 5. Сценарії роботи

### 5.1 Правка наявного

1. Розділ 1 (переказ, питання). 2. Визнач рівень правки (4.1). 3. Опорні метрики (4.5). 4. Зроби мінімальну правку. 5. Перевірки за розміром (розділ 7).

| Що міняєш                                               | Скіл                                                                            |
| ------------------------------------------------------- | ------------------------------------------------------------------------------- |
| Шрифт, розмір, переноси, довге імʼя, нерозривні пробіли | `better-typography`                                                             |
| Відступи, сітка, вирівнювання, адаптив, порядок         | `better-layout` (порядок у DOM = візуальний порядок; без `order`/`row-reverse`) |
| Радіуси, тіні, оптика, стани                            | `better-ui` як довідка значень, коли `STYLE-LOCK.md` мовчить                    |
| Контраст, сірі відтінки                                 | `better-colors` (міряє пари)                                                    |
| Фокус, клавіатура, імена кнопок, `alt`                  | `better-accessibility`                                                          |
| Мікротексти, підписи, title/description                 | `better-writing`                                                                |
| Телефон, скрол, safe-area, висота екрана                | `mobile-native`                                                                 |
| Вимога без виміру                                       | перелік варіантів або `variant` (запускає власник)                              |

### 5.2 Додавання нового елемента або секції

1. Розділ 1 обовʼязково: місце на сторінці, контент, чи входить у стек, що з SEO / якорями.
2. `STYLE-LOCK.md` і сусідні секції як зразок: бери наявні патерни, а не вигадуй нових.
3. Скіли: `landing-page-design` (лише Part A: структура, копірайт, SEO), `better-layout`, `better-typography`, `better-colors`, `better-writing`, `better-accessibility`. Якщо власник надав макет Figma чи зображення: `build-design` з токенами проєкту. Новий примітив shadcn: `shadcn`, з перестилізацією під токени.
4. Для стеку карток: перевір `--stack-h` (розділ 7). Нову картку вмикай у стек лише за згодою.
5. Додай до SEO / JSON-LD / sitemap, якщо це доречно, і запусти `check-seo`.
6. Фото: ім'я за схемою `public/img/`, `width`/`height`, `lazy` усюди, крім першого екрана.

### 5.3 Видалення

1. Знайди все повʼязане: компонент, дані в `config.ts`, імпорти, `id`, якорі й посилання меню, JSON-LD, FAQ-схему, `alt`, підписи, файли фото.
2. Покажи власнику перелік, якщо видалення зачіпає SEO, стек карток або спільні дані.
3. Видали все повʼязане, мертвого коду не лишай.
4. `better-layout` на сусідніх блоках (немає порожніх проміжків). Перерахуй `--stack-h` усіх карток. `build` + `check-seo`.

### 5.4 Тексти й фото

Тексти дослівно (4.7). Фото: природні пропорції, обличчя не обрізані, `alt` українською. Нові формулювання не повинні ламати розкладку: `break-ui` на довгі рядки.

### 5.5 Анімації

Нова: `animate` (+ `animation-vocabulary`, щоб назвати ефект, коли власник описує його словами; погодь термін у переказі). Перевірка: `animation-performance` (ривки), `review-animations` (див. розділ 6). Пошук місць для руху: `find-animation-opportunities` лише за запитом. Аудит усього сайту: `improve-animations` лише за запитом (повертає план, не змінює код).
Reveal тексту: за зразком `staggered-word-reveal`, реалізація на framer-motion або IntersectionObserver. `masked-reveal` не використовувати: він вимагає GSAP.

### 5.6 Мобільна поведінка

`mobile-native` (висота екрана, touch, safe-area) і `animation-performance` (скрол). Правила Safari 26+: колір шторки береться з fixed/sticky елемента, `theme-color` ігнорується; Telegram не віддає safe-area (завжди 0). Це вже вирішено, не перевідкривай. Рекомендація скіла «`theme-color` для кожної схеми» тут не застосовується: сайт лише темний.

### 5.7 SEO і деплой

Аудит: `marketing:seo-audit` за запитом (лише рекомендації). Тексти title / description: `better-writing`. Індексація лише в Production з `VITE_SITE_URL`. Після зміни: `npm run build`, потім `node --experimental-strip-types scripts/check-seo.mjs`. Превʼю в Telegram кешується глобально: оновлюється через @WebpageBot.

### 6.2 Запускає лише власник (`disable-model-invocation`): інструмент Skill їх не викличе

`interface-review`, `review-animations`, `break`, `state-machine`, `variant`, `prototype`, `pick-ui-library`.

Як з ними працювати:

- `interface-review` і `review-animations` обовʼязкові для M (якщо була анімація) і L. Прочитай `~/.claude/skills/<назва>/SKILL.md` (для анімацій ще `STANDARDS.md`) і виконай їхній метод вручну на своїй різниці. У звіті познач «виконано за SKILL.md, не через команду». У кінці дай власнику готові команди: `/interface-review` і `/review-animations <файли>`.
- Запуск без конкретної цілі ці скіли відповідають шаблонною фразою. Власнику передавай команду з ціллю.
- `state-machine`: якщо треба побачити всі стани компонента (FAQ відкрито / закрито, меню, hover / focus). `variant` і `prototype`: коли власник просить «покажи кілька варіантів». Пропонуй йому запустити, самостійно не імітуй.
- `pick-ui-library`: нові бібліотеки не потрібні.

### 6.3 Конфлікти, про які треба памʼятати

- `tastemaker` у режимі build створює `.tastemaker/`, `~/.tastemaker`, змінює макроструктуру та забороняє довге тире в усіх текстах. Це суперечить затвердженому стилю та дослівним текстам власника (у них довге тире є). Режим build не запускати. Зауваження `anti_slop_scan` про довге тире ігнорувати. Джерело стилю тут `STYLE-LOCK.md`, а не `.tastemaker/style-lock.md`.
- `masked-reveal` і `gsap-*`: потребують GSAP. Залежність не додавати.
- `progressive-blur` (`backdrop-filter`): суперечить заборонам живого блюру та вибірці кольору шторки Safari. Без моєї згоди не застосовувати.
- `review-animations` визначає тривалість > 300 мс і «непотрібний» рух як зауваження. Для редакційних анімацій лендінгу це не завжди недолік. Не скорочуй і не видаляй затверджений рух без моєї згоди: зафіксуй у звіті як пропозицію.
- `better-ui`, `better-typography`, `landing-page-design` Part B пропонують власні значення. Діє `STYLE-LOCK.md`.
- `frontend-design`: задає естетичний напрямок, не використовувати.

### 6.4 Оцінка до цілі (`workflow-score-to-target`)

Для L або на мою вимогу («доведи до 9/10»): рубрика з кількох критеріїв, оцінки за вимірюваннями (метрики, ширини, контраст), а не за враженням. Для L оцінку дає окремий субагент, що не бачив процесу. Оцінки не округляй угору, слабкі пункти називай. Скіл посилається на `workflow-progress-screenshots`, якого тут немає: візуальні знімки лише якщо є інструмент, інакше позначай як «не перевірено». Файли `qa/` у репозиторії не створюй.

### 6.5 Інші скіли на ПК власника

Прочитані (перевірено за `SKILL.md`):

- `ui-ux-pro-max`: **заборонено**. Спрацьовує на будь-яку UI-роботу, генерує «дизайн-систему» з бази 67 стилів / 96 палітр / 57 шрифтових пар, може створити `design-system/MASTER.md` і перебити `STYLE-LOCK.md`. Не викликати й не запускати його `search.py`, навіть якщо підказує опис.
- `gsd-*` (65 скілів, фреймворк «get-shit-done»): працюють через `.planning/` і `~/.claude/get-shit-done`, ведуть фази, плани й milestones. Для цього сайту це зайве. Самостійно не викликати. Якщо власник сам запустив `/gsd-…`, `.planning/` не комітити. Для дрібних задач `gsd-fast` не використовувати: діють розділи 1–7 цього файлу.

Не прочитані (у скопійованій папці це порожні посилання; класифіковано за назвою, перед першим використанням прочитай їхній `SKILL.md` і звір із розділами 3–4):

- `gsap-*` (core, frameworks, performance, react, scrolltrigger, timeline): не використовувати (проєкт на framer-motion і CSS).
- `apple-design`: чужа дизайн-система, джерелом стилю не є, лише довідка за запитом.
- `shadcn`: див. таблицю 6.1.
- `ask-sonner` (toast), `animate-expo` (React Native), `write-swift`, `technical-drawing`, `find-skills`, `synced`: до задач сайту не стосуються. `explain-interface`: лише якщо власник просить пояснити інтерфейс.

### 7.1 Технічні критерії

`scrollWidth ≤ innerWidth` на всіх ширинах; на `scrollY = 0` жоден елемент hero не має `top < 0`, hero вміщується на десктопних висотах 700–1080; `--stack-h` дорівнює реальній висоті картки; немає `overflow-x: hidden` на `body`; нових залежностей немає.

### 7.2 Візуальні критерії

Ширини: 320, 375, 390, 430, 600, 767 і 768 (межа), 1024, 1366, 1440, 1920, 2560, плюс ландшафт 667×375; десктоп із масштабом 125 %. Зміна розміру вікна Chrome не змінює `innerWidth`, тому використовуй тимчасову сторінку з `<iframe src="/">` потрібної ширини (або Playwright чи DevTools, якщо вже є; не ставити без дозволу). Тимчасові файли не комітити й видалити.
На кожній ширині: нічого не обрізано й не накладається; імʼя не перекриває текст чи обличчя на фото; фото мають пропорції файлу; картки лягають одна на одну, затемнення нижньої плавне; інваріанти краси 4.4 дотримані.

### 7.3 Що агент перевірити не може

Реальні пристрої. У кожному підсумку дай власнику короткий чеклист для iPhone: Safari, Telegram, Instagram (верх hero на `scrollY = 0`, повільний скрол і fling, bounce угорі, шторка, проходження карток, меню і Instagram-лінк). Локально: `npm run dev -- --host`, відкрити `http://<IP>:5173`; продакшн-збірка: `npm run build`, потім `npm run preview -- --host`.
